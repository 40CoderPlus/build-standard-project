# Mandatory AI review system

AI review is a required quality gate for every material code, contract, migration, configuration, security, product-behavior, or deployment change.

## Independence

Preferred order:

1. a separate AI reviewer agent with no implementation context;
2. a fresh task/context that receives the requirement, authoritative sources, raw diff, and test evidence;
3. only when neither exists, a clearly separated review pass after discarding implementation conclusions.

Do not pass the intended answer, expected findings, or implementer self-assessment to the reviewer.

## Review inputs

- requirement and acceptance IDs;
- authority order and relevant baselines;
- raw Git diff and changed-file list;
- affected contracts, migrations, generated artifacts, and configuration;
- exact automated-check output;
- known `BASELINE_GAP` items;
- deployment/recovery impact.

## Review dimensions

The reviewer must check:

1. product drift and scope;
2. requirement/acceptance traceability;
3. architecture and package boundaries;
4. API/event compatibility;
5. data invariants, migrations, idempotency, concurrency, and rollback;
6. authorization, privacy, secrets, and hidden-field leakage;
7. AI provenance, consent, review, and prohibited-use boundaries;
8. UI states, i18n, accessibility, and responsive behavior;
9. tests, skipped checks, coverage, and false-positive gates;
10. observability, operations, deployment, smoke, and recovery;
11. dependency, license, supply-chain, and configuration risk;
12. unrelated changes, generated noise, and user-work preservation.

## Findings

Use severities:

- `blocker`: unsafe, destructive, unauthorized, corrupting, or fundamentally off-spec.
- `high`: likely product drift, security/privacy defect, data loss, broken contract, or missing critical test/recovery.
- `medium`: meaningful maintainability, edge-case, accessibility, observability, or test weakness.
- `low`: bounded improvement with little delivery risk.

Each finding contains title, evidence, affected files/lines, violated rule or acceptance ID, impact, and recommended action.

## Gate policy

- `blocker` and `high` findings block acceptance and deployment.
- `medium` findings require a fix or a documented owner, reason, expiry, and follow-up requirement.
- `low` findings may be accepted into backlog.
- After fixes, rerun affected automated checks and AI review.
- Validate the final report with `pnpm review:ai:check`.

Human review may add findings but is not a default prerequisite. AI review must never be waived merely because the change was generated by a trusted model.

## Report

Write `artifacts/ai-review/<REQ-ID>-<timestamp>.json` using the bundled example schema shape. Include:

- reviewer agent/model, independent-context mode, reviewer session ID, and a different implementation session ID;
- every material current changed file in `change.files` and every deleted path in `change.deletedFiles`;
- for a local review without deletions, the exact fingerprint from `pnpm review:fingerprint -- <files...>` as `change.contentHash` and `change.diffId`;
- for CI, release, or any review containing deletions, the output of `pnpm review:fingerprint -- --base <full-base-sha>`, including `baseSha`, `headSha`, `contentHash`, `gitDiffHash`, and `diffId`;
- requirement and acceptance IDs;
- passing check evidence; `fail` and `not_run` do not satisfy the gate;
- findings and resolutions;
- final verdict: `pass`, `pass_with_followups`, or `fail`;
- generated and completed timestamps.

Never fabricate reviewer identity, independence, commands, or evidence.

The validator recomputes the content fingerprint and, when `AI_REVIEW_BASE_SHA` is available, binds the report to the resolved base SHA, current head SHA, current/deleted file sets, and SHA-256 of the exact binary Git diff. A same-base/head, partial, historical, or deletion-blind report cannot approve the change. Repository validation can bind evidence to files, but it cannot cryptographically prove who controlled an AI session; use a separate Agent/task and preserve its real session metadata. For higher-assurance environments, add a signed external reviewer attestation without making human review a default blocker.
