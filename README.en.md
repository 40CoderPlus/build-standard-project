# build-standard-project

[简体中文](README.md) | [English](README.en.md)

An engineering Skill for AI-assisted development. It helps Codex, Claude Code, and other compatible agents establish a project foundation and follow consistent engineering practices as the project evolves.

It covers two main workflows: **choose technology and deployment options that fit the product during initialization, then handle everyday development through focused changes, relevant tests, and a concise change record.**

Current version: `1.9.0` · [Change history](CHANGELOG.md) · [MIT License](LICENSE)

## What you can do with it

| Scenario | Capabilities | How it starts |
| --- | --- | --- |
| Everyday development | Fix bugs, optimize behavior, adjust UI, and refactor locally, with checks scoped to the change | Routine is the default mode |
| Project initialization or adoption | Compare technology and deployment options; establish source layout, engineering rules, tests, and CI | Explicitly request initialization, standardization, adoption, or rebuilding |
| Repository audit | Report prioritized findings with evidence | Explicitly request an audit; no edits by default |
| Release preparation | Add validation for release and high-risk boundaries | Explicitly request release-related work |
| Legacy project migration | Replace outdated engineering controls in projects generated by versions 1.1–1.6 | Explicitly request migration; preview the plan before applying it |
| Conversation organization | Rename conversations in the current project using a consistent format | Trigger manually; requires host support |

The agent reads and executes the Skill's instructions. Installing it does not automatically initialize existing projects or schedule background work. This repository also includes a project generator and a legacy migration script for the corresponding workflows.

## Installation and quick start

### 1. Install the Skill

Clone the repository and run the installer for your operating system. Git must be available locally. The installer copies the Skill into the Codex, Claude Code, and shared agent skill directories, backing up each existing installation before replacing it.

**Windows PowerShell**

```powershell
git clone https://github.com/40CoderPlus/build-standard-project.git
cd build-standard-project
.\install.ps1
```

**macOS / Linux**

```bash
git clone https://github.com/40CoderPlus/build-standard-project.git
cd build-standard-project
chmod +x install.sh
./install.sh
```

| Agent | Default installation path | Environment variable for a custom root |
| --- | --- | --- |
| Codex | `~/.codex/skills/build-standard-project` | `CODEX_HOME` |
| Claude Code | `~/.claude/skills/build-standard-project` | `CLAUDE_CONFIG_DIR` |
| Other compatible agents | `~/.agents/skills/build-standard-project` | `AGENTS_HOME` |

On Windows, `~` corresponds to `%USERPROFILE%`. Restart the agent or start a new task after installation.

### 2. Use it in your project

Invoke the Skill in a task opened for your target project, for example:

```text
Use $build-standard-project to fix the login failure.
```

Once invoked, the Skill routes ordinary development work to Routine. You do not need to repeat “do not initialize the project” for each task. Examples for initialization, audits, and other operations appear below.

If your agent cannot discover Skills natively, ask it to read `skills/build-standard-project/SKILL.md` in this repository, then load only the reference documents relevant to the current task.

### 3. Update an installed Skill

In your cloned repository, run:

```bash
git pull --ff-only
```

Then rerun `install.ps1` or `install.sh` and start a new task. **Updating the Skill does not migrate engineering rules inside existing projects.** See [legacy project migration](#legacy-project-migration) for projects generated by older versions.

## Everyday development: keep work scoped to the change

Routine covers bug fixes, optimizations, UI adjustments, and local refactoring:

1. Read the relevant code, tests, and project constraints.
2. Add a concise description of the requirement change, optimization, or bug to the existing change record. Generated projects use `docs/changes.md`.
3. Make the smallest coherent change and add or update directly affected tests. Bug fixes require regression tests.
4. Run the affected test file and review the final diff. Rerun checks only when they fail or subsequent edits invalidate the result.

For example, a project using pnpm should prefer the relevant test file:

```bash
pnpm test -- path/to/affected.test.ts
```

Checks serve different purposes at different stages:

| Stage | Scope |
| --- | --- |
| Small everyday changes | Directly affected tests and final-diff review; no full quality suite, coverage, E2E, or visual testing by default |
| Code commits | Formatting and linting for relevant staged files, plus Conventional Commit message validation |
| CI | Checks appropriate to the stack, including a lightweight check that behavior-source changes have a change entry and related tests |
| High-risk changes or releases | Additional validation for affected security, permissions, money, privacy, migration, public contract, infrastructure, or deployment boundaries |

`quality:fast` is available for CI or situations that need feedback from the full unit-test suite. Type checks, builds, and E2E tests stay outside commit hooks. Routine tasks do not require an independent reviewer, a separate review file, or deployment evidence.

## Initialization: choose an approach, then build the foundation

Explicitly request initialization or standardization:

```text
Use $build-standard-project to initialize this project. First recommend technology and deployment options based on the product requirements, explain their costs and limitations, and let me choose before generating the project.
```

### How options are selected

The agent considers product scale, team needs, traffic, data, budget, and operational constraints. It recommends the simplest sufficient option and presents an upgrade option when actual requirements justify one. Generation begins after you choose an option or explicitly delegate that decision to the agent.

Components such as Redis, queues, separate APIs, microservices, Kubernetes, and multi-region infrastructure require supporting requirements and explicit user selection. Confirmed decisions are recorded and revisited only when new evidence warrants it.

### What initialization delivers

| Output | Purpose |
| --- | --- |
| `.project/standard-project.json` | Technology and deployment decisions, alternatives considered, and conditions for revisiting them |
| `AGENTS.md` | Canonical project engineering rules and the everyday development workflow |
| Application code and module directories | Boundaries appropriate to the selected architecture, without unused applications or infrastructure packages |
| `docs/product/`, `docs/architecture/`, `docs/engineering/` | Product constraints, architecture, and engineering instructions |
| `docs/changes.md` | One record for requirement changes, optimizations, bugs, and related tests |
| Tool configuration and Git hooks | Formatting, linting, types, tests, builds, and commit conventions |
| CI, deployment configuration, and example environment variables | Stack-appropriate validation, deployment checks, and recovery guidance |

Commit checks, a change record, directly affected tests, bug regression tests, and CI/release commands are part of the initialization baseline and are established with the selected approach. Initialization also includes implementing and validating one representative end-to-end product flow. Generating directories alone does not mean the product is complete.

### Bundled generator support

**The bundled generator currently supports only the combination of `modular-monolith` and `container-generic` deployment.** The Skill can guide other approaches, but the agent must implement the selected approach directly or extend the generator.

Normally, the agent handles initialization. To invoke the script directly, first use the [profile documentation](skills/build-standard-project/references/project-profile.md) and [example configuration](skills/build-standard-project/assets/project-profile.example.json) to prepare an approved configuration. Then run this command from the repository root:

```bash
python skills/build-standard-project/scripts/scaffold_project.py \
  --config path/to/project-profile.json \
  --output path/to/project
```

The example configuration contains pending selections and must not be treated as an approved plan. After generation, run these commands in the target project:

```bash
pnpm install
pnpm format
pnpm quality
```

See the [initialization workflow](skills/build-standard-project/references/init-workflow.md) and [generation contract](skills/build-standard-project/references/generation-contract.md) for the full process and acceptance requirements.

## Additional workflows

### Audits and release preparation

To inspect a repository and report findings:

```text
Use $build-standard-project to audit this repository. Report findings and evidence only.
```

To prepare for a release:

```text
Use $build-standard-project to identify risks and validation gaps for this release.
```

Audits do not modify files by default. Release work validates affected boundaries without repeating initialization. See [quality checks](skills/build-standard-project/references/quality-checks.md) and the [deployment guide](skills/build-standard-project/references/deployment-system.md).

### Legacy project migration

This workflow applies to **projects generated by versions 1.1–1.6**. If small changes remain slowed down by legacy `quality:full`, coverage, fingerprint, or AI Review requirements after updating the Skill, the project's own `AGENTS.md`, `package.json`, and CI need a separate migration.

Preview the migration plan without modifying the project:

```bash
python skills/build-standard-project/scripts/migrate_legacy_project.py \
  --project path/to/existing-project
```

After confirming the plan, apply it:

```bash
python skills/build-standard-project/scripts/migrate_legacy_project.py \
  --project path/to/existing-project \
  --apply
```

The migrator handles only known legacy generated templates and stops when it encounters a custom `AGENTS.md`. After applying the migration, run `pnpm prepare` once in the target project to enable repository-local commit hooks. See the [legacy migration guide](skills/build-standard-project/references/legacy-upgrade.md).

### Normalize conversation titles

```text
Use $build-standard-project to normalize conversation titles in the current project. Change titles only; keep the project name and all other state unchanged.
```

This is a manually triggered batch operation. Titles use `MMDD｜TYPE｜Topic`, for example `0903｜FIX｜Login failure`.

- The date comes from the conversation's `createdAt`, converted to `Asia/Shanghai`.
- Default type codes are `FEA` (feature), `DES` (design), `FIX` (bug fix), `OPT` (optimization), `REL` (release), `EXP` (exploration), `DOC` (documentation), and `RES` (research). Chinese type labels are used only when explicitly requested.
- Conversations retain their original titles when the creation time is missing or the type or topic cannot be determined.
- The host must support listing conversations in the current project, reading their creation times, and updating titles independently. Without these capabilities, renaming cannot proceed.

See the [conversation title rules](skills/build-standard-project/references/conversation-titles.md) for full details.

## Repository layout and maintenance

The Skill itself lives in `skills/build-standard-project/`. The repository root contains installation scripts, documentation, and tests for this tool.

```text
skills/build-standard-project/
  SKILL.md                      # Agent entry point and task routing
  agents/openai.yaml            # Agent metadata
  references/                   # Detailed rules loaded by workflow
  assets/                       # Configuration examples and project templates
  scripts/
    scaffold_project.py         # Project generator
    migrate_legacy_project.py   # Legacy project migrator
install.ps1                     # Windows installer
install.sh                      # macOS / Linux installer
tests/                          # Regression tests for this tool
```

When developing this tool, run its lightweight regression suite from the repository root:

```bash
python -m unittest discover -s tests -v
```
