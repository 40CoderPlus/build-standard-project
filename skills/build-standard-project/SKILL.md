# Build Standard Project

Version: **1.8.3**

## Route

- **Routine (default):** scoped bug, optimization, UI change, or refactor. Use the fast path below.
- **Init/adopt:** only when explicitly asked to initialize, scaffold, standardize, adopt, or rebuild. Read [init-workflow.md](references/init-workflow.md).
- **Legacy upgrade:** when explicitly asked to migrate a project generated by v1.1-v1.6, read [legacy-upgrade.md](references/legacy-upgrade.md). Installing a new Skill alone does not migrate project-local rules.
- **Audit:** report prioritized gaps; do not modify unless asked.
- **Release:** read [quality-checks.md](references/quality-checks.md), [independent-review.md](references/independent-review.md), and [deployment-system.md](references/deployment-system.md). Do not repeat Init.

Do not upgrade Routine to Init because this skill or its generated rules exist in the repository.

## Work style

- Keep the quality floor: the smallest coherent change, final-diff review, the narrowest relevant test, and honest reporting.
- Treat efficiency as part of quality. Anything beyond that floor needs affected-risk evidence or an explicit user request; unnecessary process, architecture, deliberation, narration, and repeated validation are defects.
- Infer reversible details. Ask only when a missing decision materially changes behavior, architecture, cost, or risk; batch it once with a recommendation.
- Once decided, execute. Reopen a decision only when new evidence makes it invalid.
- Prefer the minimum sufficient design. Do not propose or implement a more complex component unless simpler options are inadequate for an approved product requirement.
- Redis, queues, workers, separate APIs, search clusters, microservices, Kubernetes, multi-region, or similar complexity require explicit user selection before implementation.
- After material costs, limits, and risks are stated, the user owns the selected product/architecture/operations tradeoff. AI still owns truthful disclosure and correct in-scope implementation; this is not permission to hide known risk or bypass safety/legal constraints.

## Routine fast path

1. Inspect only relevant code, tests, contracts, and root instructions.
2. For a requirement change, optimization, or bug fix, add a concise entry to the repository's existing change record; generated projects use `docs/changes.md`.
3. Make the smallest coherent change and preserve unrelated work.
4. Add or update a directly affected test. A bug fix requires a regression test that demonstrates the failure before the fix and passes after it.
5. Run the directly affected test file, then review the final diff. Do not substitute `quality`, `quality:full`, coverage, or E2E for a scoped test.
6. Rerun only a failed check or one invalidated by later edits.

The change entry records the type, observable change, and test path. It is the only routine traceability artifact; do not add IDs, lifecycles, fingerprints, or duplicate ledgers. Routine work does not require an independent reviewer, aggregate quality gate, E2E/visual suite, deployment evidence, or long handoff unless the user explicitly asks.

Expand validation only for the affected boundary: security/privacy, money/entitlements, irreversible data, migration/public contract, shared infrastructure, deployment, or product-AI governance. Use existing product documents and request a focused independent review only when high-risk, release-bound, or explicitly required; do not invent machine-readable control systems.

## Finish

Stop when the change record and directly affected tests are current and proportionate checks pass. Reply with only the outcome, key test/review evidence, and material risk or required user action. Never weaken checks or fabricate evidence.
